# 2차 마일스톤 장애 주입 실험 결과

- 실행일: 2026-11-26
- 대상 커밋: `feat/m2-gb10-inject` 브랜치
- 환경: ARM64 GPU 장비 1대, 실제 LLM 서빙 엔진 + 압축 일 주기 부하 + 예약 장애 주입 + 정답 라벨
- 방법과 도구: `examples/inject-lab/README.md`, 평가 정의는 `docs/evaluation.md`
- 합성 데이터 결과: `docs/results/m1-baseline.md`
- 수치는 `python -m anomaly_detection.lab.replay` 출력 그대로. 데이터 파일은 레포에 두지 않고 장비의 `~/work/anomaly-data/gb10-inject-20261126/`에 보관

## 요약

- 요청량 급락과 출력 길이 급감은 신호가 크게 움직였고(정상 대비 3%, 2%) seasonal과 고정 임계 모두 5건 중 5건 탐지
- 처리량 하락(GPU 경쟁 프로세스)은 신호가 건마다 0.38배에서 0.96배로 들쭉날쭉했고 seasonal 탐지는 5건 중 2건
- 지연 증가는 1차 실행에서 신호가 거의 안 움직였고(중앙값 1.23배) 주입을 세게 한 2차 실행에서는 2배 가까이 움직였지만(중앙값 1.98배) 어떤 모델도 5건 중 0건 탐지
- 합성 데이터에서 0이던 seasonal 오탐이 실데이터에서는 4개 신호 합산 하루당 신호당 0.60건
- RCF는 시나리오 전체에서 탐지율 0.15로 합성 결과(0.85에서 1.00)보다 크게 낮음. 원인은 확인하지 못함
- 사이드카를 실제로 띄워 얻은 실시간 점수는 같은 데이터를 seasonal로 재생한 결과와 거의 같음(탐지 13건 대 13건, 오탐 22건 대 21건)

장비는 다른 작업과 함께 쓰는 상태였음. 호스트 부하(1분 평균, 20코어)는 1차 중앙값 16.8(10분위 9.7, 90분위 37.8), 2차 중앙값 11.9. GPU 계산 프로세스는 시작 직후와 실행 중 한 번 확인했을 때 이 실험의 엔진뿐이었고 그 뒤로는 확인하지 않음.

## 주입 방법과 신호 확인

효과 크기는 이벤트 시작 60초 뒤부터 끝까지 해당 신호의 중앙값을 시작 전 180초 중앙값으로 나눈 값.

| 시나리오 | 주입 방법 | 감시 신호 | 이벤트 수 | 효과 크기 중앙값 | 최소 | 최대 | 판정 |
|---|---|---|---|---|---|---|---|
| request_drop | 부하 생성기 도착률 0.03배 | 완료 요청 수 비율 | 5 | 0.03 | 0.02 | 0.05 | 신호 생성됨 |
| output_length_drop | 출력 토큰 상한 1에서 3(HTTP 200 유지) | 요청당 생성 토큰 | 5 | 0.02 | 0.02 | 0.02 | 신호 생성됨 |
| throughput_drop | 같은 GPU에서 경쟁 행렬곱 프로세스(듀티 1.0) | 디코딩 속도(토큰 간 지연의 역수) | 5 | 0.68 | 0.38 | 0.96 | 신호 생성됨, 크기는 건마다 큰 차이 |
| latency_rise, 1차(청크당 0.06초 지연) | 클라이언트 경로에서 응답 청크 읽기를 지연 | 클라이언트 요청 지속시간 | 5 | 1.23 | 0.42 | 1.75 | 신호 거의 안 움직임 |
| latency_rise, 2차(청크당 0.15초 지연) | 같은 방법, 지연만 증가 | 클라이언트 요청 지속시간 | 5 | 1.98 | 1.49 | 2.99 | 신호 생성됨 |

- 전력 상한과 클럭 고정은 쓰지 못함. `nvidia-smi`에서 전력 상한이 N/A이고 클럭 고정 시도(`-lgc`)는 권한 오류. root가 필요한 `tc netem`도 쓰지 않음
- GPU 경쟁 부하의 효과를 사전 확인(경쟁 없음 48.3ms, 듀티 1.0에서 93.6ms, 듀티 0.5에서 63.9ms, 경쟁 종료 뒤 45.4ms, 토큰 간 지연 평균)
- 처리량 하락 5건의 효과 크기는 0.44, 0.68, 0.38, 0.96, 0.72. 하루 중 14시에서 16시 구간에 시작한 두 건이 0.96과 0.72로 가장 약했음. 원인은 확인하지 못함
- 지연 증가는 클라이언트 쪽 읽기 지연이라 엔진이 보는 지연 히스토그램은 구조상 움직이지 않음(실측은 하지 않음). 읽기 지연이 토큰 생성과 겹쳐 진행되므로 청크당 0.06초(생성 약 0.048초)로는 요청 지속시간이 그만큼 늘지 않음. 그래서 2차에서 0.15초로 올림
- GPU 경쟁 프로세스는 CUDA 초기화에 시간이 걸려 라벨 시작 시각보다 실제 경합 시작이 늦음. 그 시간은 측정하지 않음

## 합성 데이터와 비교

합성 결과(`docs/results/m1-baseline.md`)와 신호가 같지 않음. 합성의 `token_length_drop`은 여기 `output_length_drop`에 대응하고, `throughput_drop`과 `step_time_rise`는 학습 처리량 신호라 서빙의 디코딩 속도나 요청 지연과 직접 비교할 수 없음. 아래는 방향을 보기 위한 대조.

| 항목 | 합성 | 이번 실험(1차) |
|---|---|---|
| seasonal 탐지율 | 요청량 1.00, 출력 길이 1.00, 처리량 1.00, 스텝 시간 1.00 | 요청량 1.00, 출력 길이 1.00, 디코딩 속도 0.40, 지연 0.20 |
| seasonal 오탐 | 정상 시계열과 시나리오 모두 0건 | 4개 신호 합산 21건, 신호당 하루당 0.60. 요청량 0건, 출력 길이 2건, 디코딩 속도 7건, 지연 12건 |
| 고정 임계 탐지율 | 요청량 0.65, 출력 길이 1.00, 처리량 0.00 | 요청량 1.00, 출력 길이 1.00, 디코딩 속도 0.40, 지연 0.00 |
| RCF 탐지율 | 0.85에서 1.00 | 0.00에서 0.20(합산 0.15) |
| seasonal 탐지 지연 중앙값 | 2.0에서 2.5분 | 45에서 112초 |

차이로 볼 수 있는 점:

- 오탐이 0에서 늘어난 곳은 디코딩 속도와 지연 신호. 두 신호는 부하와 호스트 상태에 따라 일 주기 모양과 무관하게 흔들림. 호스트 부하 중앙값이 16.8이었던 1차와 11.9였던 2차에서 지연 오탐은 12건과 0건이라 공유 장비 잡음이 한 원인일 가능성이 있으나, 두 실행의 조건이 다르고 직접 검증하지는 않음
- 오탐의 일부는 다른 시나리오 이벤트 구간에서 발생. 1차 seasonal 오탐 21건 중 8건(출력 길이 2건, 처리량 3건, 지연 3건)이고 나머지 13건은 어느 이벤트와도 겹치지 않은 구간에서 발생
- 고정 임계가 합성보다 잘 나온 곳은 요청량. 합성에서는 변형의 절반이 정상의 10에서 50퍼센트까지만 떨어졌지만 이번 주입은 3퍼센트까지 떨어져 하한 아래로 확실히 내려감
- 합성 처리량 시나리오는 정상 시계열이 매끈하고 하락이 45에서 55퍼센트로 일정했음. 실데이터의 처리량 하락은 신호 크기가 건마다 달랐고 정상 상태 변동이 커서 seasonal 탐지율이 1.00에서 0.40으로 내려감
- RCF 탐지율은 크게 낮아짐. 요청량 신호에 대해 RCF를 다시 돌려 이벤트별 최고 점수를 보니 첫 이벤트에서만 1.00이었고 이후 네 이벤트는 0.03에서 0.11. 표본 크기 256으로 줄여도 같은 경향(첫 이벤트 0.76, 이후 0.03에서 0.32). 이후 이벤트에서 점수가 낮은 원인은 확인하지 못함
- 지연 수치는 샘플 간격이 다름(합성 60초, 이번 5초). 알림 규칙의 3샘플 연속 조건이 하한을 정하는 방식은 같음. 단순 비교는 불가


## 한계와 확인하지 못한 것

- 실행은 1회, 시나리오당 이벤트 5건. 탐지율의 신뢰구간이 매우 넓어 모델 간 순위를 가리기에 부족
- 모든 모델은 합성 데이터로 정한 기본 파라미터 그대로. 이번 데이터에 맞춰 조정하지 않음
- 압축 일 주기의 24분은 합성의 1440분과 같은 비율이 아님. 이벤트가 하루의 8에서 21퍼센트로 합성(4에서 17퍼센트)보다 약간 길고, 1분 `rate()` 창이 하루에서 차지하는 비중이 큼. 주 주기와 추세는 모사하지 않음
- 지연 증가는 클라이언트 경로 지연의 시뮬레이션이고 엔진이나 네트워크의 실제 지연이 아님
- 처리량 하락의 건별 편차 원인, GPU 경쟁 프로세스의 경합 시작 지연, RCF 탐지율이 낮은 원인, 지연 신호의 일 주기 변동 원인은 확인하지 못함
- GPU 다른 프로세스 확인은 시작 직후와 실행 중 한 번뿐이고 이후 변동은 모름. 호스트 CPU 부하는 다른 작업과 겹쳐 높았음
- 오탐 집계의 다른 주입 중 열은 구간 겹침 기준일 뿐 인과 확인이 아님
