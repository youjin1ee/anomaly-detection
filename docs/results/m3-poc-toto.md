# 3차 마일스톤 Toto 2.0 예측 구간 모델 PoC

- 실행일: 2026-11-26
- 대상: `feat/m3-poc-toto` 브랜치. 2차 통합 브랜치(NAB 하네스와 실데이터 재생 하네스 포함)에서 분기
- 모델: Datadog Toto 2.0 4m(4M 파라미터)와 22m(22M 파라미터). 코드와 가중치 모두 Apache-2.0. PyPI `toto-2` 2.0.0, torch 2.15.0(CUDA 빌드 휠이지만 GPU는 쓰지 않음)
- 실행 환경: ARM64 원격 장비, CPU 코어 4개 고정(`taskset`), 스레드 4개, 주소 공간 상한 16GB, GPU 비사용. 다른 작업과 장비를 공유해서 부하 평균이 5에서 41까지 흔들림. 시간 수치는 참고용
- 방법 정의: `docs/evaluation.md`의 NAB 절과 Toto 절
- 명령: `anomaly-detection-nab run-toto`와 `report`, `scripts/bench_toto.py`, `scripts/eval_toto_inject.py`

## 요약

- NAB standard 점수는 4m 11.5, 22m 6.8. rrcf 21.7(시드 0, 3개 시드 평균 20.4)보다 낮고 공개 점수표의 Random(11.0)과 비슷한 수준. 계절성 기준선은 0.0(null과 같음)
- `for: 3` 규칙을 입힌 점수는 4m 11.7, 22m 11.0. rrcf+for3 23.8에 못 미침
- 22m이 4m보다 낫지 않음. standard에서 오히려 낮음(6.8 대 11.5). 모델을 키워서 얻은 이득은 이 설정에서 관찰되지 않음
- 이벤트 단위로는 윈도우 116개 중 4m 1개, 22m 2개만 탐지(점수 0.5 이상 3개 연속 기준). rrcf는 42개, 계절성은 75개
- 예측 구간의 보정은 맞음. 점수가 구간 밖인 레코드 비율이 4m 19.9퍼센트, 22m 19.6퍼센트로 목표 20퍼센트에 가까움. 구간이 틀린 게 아니라 1스텝 예측 구간의 이탈이 NAB 이상과 잘 겹치지 않았음
- 장애 주입 데이터(이벤트 20개)에서는 4m, 22m 모두 0개 탐지(0.5 기준). 계절성 13개, 고정 임계 12개, rrcf 3개
- CPU 비용: 시계열 500개를 배치로 한 스텝 처리하는 시간이 4코어에서 4m 0.87초, 22m 3.83초. 1분 주기에 들어옴. 시계열 1개 단건 호출은 4m 약 30ms, 22m 약 66ms
- 판정: 운영 비용은 1분 주기에 충분히 들어오지만 이 구성의 탐지 성능은 기본 모델로 쓸 수준이 아님. 선택 확장 모델로만 두고 기본값으로 올리지 않음

## 구현

- 어댑터: `models/toto.py`. 모델 종류 `toto`로 등록. 기존 인터페이스 `update(timestamp, value) -> ModelOutput | None`을 그대로 따름
- 입력: 시계열마다 최근 `context_length`(기본 512)개 값을 유지. 새 값은 예측과 채점이 끝난 뒤에 컨텍스트에 추가되므로 채점 대상 값이 예측에 보이지 않음
- 출력: 다음 1스텝의 분위수 9개(0.1에서 0.9). lower는 0.1 분위수, upper는 0.9 분위수, expected는 중앙값
- 컨텍스트 길이 제약: 모델은 패치 32개 단위로 읽으므로 윈도우 길이는 32의 배수. 버퍼가 512보다 짧으면 32의 배수 중 가장 긴 길이를 씀. 워밍업은 `min_context`(기본 128)개 이전에 값을 내지 않음(None)
- 결측 처리: 파이프라인이 결측과 시간 역행을 0으로 바꾸지 않고 건너뜀. 어댑터는 유한한 값만 받음
- 분위수가 유한하지 않으면 그 스텝은 값 없음(None)
- 의존성: 선택 extra `toto`(`toto-2`, `torch`). 기본 설치에는 들어가지 않음. 어댑터 모듈은 모델을 처음 만들 때 torch를 불러옴. extra를 설치하면 `uv.lock`에 약 2000줄이 늘어남(gluonts, lightning, CUDA 휠 의존성 포함)
- 가중치: 레포에 넣지 않음. 체크포인트 디렉터리(`config.json`, `model.safetensors`)를 `model_dir`로 지정

### 점수 매핑

- 정의: 값이 구간 [lower, upper] 밖으로 벗어난 거리 d(구간 안이면 0)를 구간 폭 w로 나눈 r = d / w. 점수 = r / (r + 1)
- 구간 폭의 하한: 중앙값의 2퍼센트(다른 모델의 `min_scale_ratio`와 같은 값). 평평한 시계열이 구간 폭 0을 만들어 모든 흔들림을 이상으로 보는 일을 막음
- 값의 의미: 구간 안은 0. 구간 끝에서 폭 하나만큼 벗어나면 0.5(알림 기본 임계). 아주 먼 이탈은 1에 수렴
- 선택 근거
  - 구간 폭으로 정규화하면 시계열 단위와 크기에 상관없이 같은 임계를 쓸 수 있음
  - 구간 폭은 그 시점 모델의 불확실성이라 변동이 큰 구간은 같은 이탈도 낮게 채점됨
  - r이 폭 하나일 때 0.5로 둔 이유는 알림 규칙이 0.5를 쓰기 때문. 가우시안 잡음 가정에서 0.1에서 0.9 구간 폭이 2.56 시그마라서 0.5는 중앙값에서 약 3.8 시그마에 해당
  - 점수가 r에 대해 단조 증가라서 NAB 점수(코퍼스에서 임계값을 고름)는 이 상수에 영향을 받지 않음. 0.5 고정 임계 점수와 이벤트 지표만 영향을 받음
- 이 상수는 첫 실행 전에 정했고 결과를 본 뒤 바꾸지 않음. 상수와 컨텍스트 길이에 대한 민감도는 측정하지 않음

### 배치 경로와 같은 결과인지

- 스트리밍 경로: `TotoModel.update`로 한 레코드씩. 사이드카가 쓰는 방식
- 오프라인 배치 경로: `score_batch`가 한 시계열의 여러 시점 윈도우를 한 번의 순전파로 예측. NAB 전체(레코드 365558개)를 4m은 1181초, 22m은 3730초에 처리
- 두 경로의 윈도우는 같은 규칙(직전 값들, 길이는 32의 배수, 채점 대상 값은 제외)으로 만듦
- 확인
  - 가짜 엔진으로 단위 시험: 점수, 기대값, 하한, 상한이 두 경로에서 일치. NAB 파일 형태(중복 타임스탬프, 시간 역행, 결측 포함)에서도 일치(`tests/test_nab_toto.py`)
  - 실제 4m과 22m 네트워크로 단위 시험(환경변수 `TOTO_MODEL_DIR` 지정 시 실행): 둘 다 통과. 허용오차는 하한, 기대값, 상한이 구간 폭의 0.1퍼센트, 점수가 0.001. 두 경로 차이의 실제 최댓값은 재지 않음. NAB 실행 자체는 배치 경로만 사용

## 운영 현실성 측정 (CPU만)

- 방법: `scripts/bench_toto.py`. 모델 크기마다 별도 프로세스, 컨텍스트 512, 합성 시계열(일 주기 파동에 잡음). 측정 중 부하 평균 약 6
- 단건: 시계열 1개의 한 스텝. forward는 모델 호출만, update는 `TotoModel.update` 전체(윈도우 만들기, 채점 포함). 100회
- 배치: 시계열 500개를 윈도우 500개로 묶어 한 번에 한 스텝. 5회 중앙값(괄호는 최소와 최대)

### 1분 주기 판정

- 판정: 들어옴. 단 시계열 500개, 코어 4개, 컨텍스트 512 조건
  - 배치 호출: 4m 0.87초(주기의 1.5퍼센트), 22m 3.83초(6.4퍼센트). 코어 1개에서도 4m 2.79초, 22m 16.96초로 60초 안
  - 단건 호출 500번: 4m 약 14초, 22m 약 31초(계산값). 지금 사이드카 구조(시계열별 스레드가 단건 호출)에서도 60초 안이지만 22m은 여유가 절반 수준이고 torch 스레드들이 서로 코어를 다툼
- 사이드카 현재 구조는 배치 호출 경로가 없음. 배치 이득(4m에서 약 16배, 22m에서 약 8배)을 쓰려면 한 주기에 모든 시계열의 윈도우를 모아 한 번 호출하는 경로를 사이드카에 추가해야 함. 이번 PoC에서는 만들지 않음
- 측정하지 않은 것: 시계열 500개를 넘는 규모(선형으로 늘어난다고 가정하지 않음), x86 장비, 질의 시간과 로딩 시간을 합친 주기 전체 시간
- 비용 대비 효과: 비용이 문제는 아님. 4m의 NAB standard 점수가 22m보다 높아서 큰 모델을 쓸 이유도 이번 측정에서는 없음

## 장애 주입 데이터 평가

- 데이터: 장애 주입 실험의 첫 본 실행(`run1`). 실행 기록(`run.out`)에 완료 표시가 있고 라벨 파일과 신호 파일이 완성되어 있음을 확인한 뒤 읽기 전용으로 사용. 폴더에는 쓰지 않음. 같은 폴더의 `run2-latency`는 다른 실험이라 평가하지 않음
- 구성: 신호 4개(요청률, 출력 토큰 수, 디코드 속도, 클라이언트 지연), 5초 간격, 시계열당 약 3680개 샘플, 완료된 주입 이벤트 20개(신호당 5개). 실험 하루는 1440초로 압축. 앞 4일(실험 시간)은 워밍업
- 방법: 하네스의 알림 규칙(점수 0.5 이상 3개 연속)과 이벤트 매칭을 그대로 사용. 신호마다 시나리오가 정한 방향(요청률, 출력 토큰, 디코드 속도는 하락, 지연은 상승)을 적용. fixed, seasonal, rcf는 압축한 하루를 86400초로 되돌린 시간으로 돌려 일 주기 기본값을 씀(이 실험의 재생 방식을 따름). Toto는 시간 정보를 쓰지 않고 5초 샘플을 그대로 받음
- fixed, seasonal, rcf 수치는 이 문서의 스크립트로 다시 돌린 값. 장애 주입 실험의 중간 보고서는 완료 이벤트 9개 시점의 값이라 직접 비교하지 않음

## 해석

- 1스텝 예측 구간은 천천히 변하는 이상을 곧 따라감
  - 장애 주입 신호의 이벤트 12개(신호당 3개)에서 이벤트 시작 직후 10개 샘플을 확인. 예측 하한이 값과 거의 같은 속도로 내려감. 이 신호들은 1분 rate 창이라 주입이 급락이 아니라 경사로 나타남
  - 이 12개 이벤트에서 이벤트 구간 안 최대 점수는 0.10에서 0.76 사이였고 0.5를 넘긴 것은 몇 개 샘플에 그쳐 3개 연속 조건을 채우지 못함
  - 원인이 경사 추종이라는 설명은 위 관찰에서 나온 가설이고 컨텍스트 길이나 다단계 예측으로 바꿔 확인하지는 않음
- NAB에서도 같은 이유일 가능성이 있으나 확인하지 않음. 수준 이동처럼 지속되는 이상은 몇 샘플 뒤 컨텍스트에 들어가 예측 구간이 새 수준으로 옮겨 감. NAB 파일별로 이 가설을 따져 보지는 않음
- 22m이 4m보다 낫지 않음. 두 모델의 점수 분포(구간 밖 비율, 0.5 이상 비율)는 거의 같고 NAB 차이(standard 6.8 대 11.5)는 임계값 하나를 코퍼스에서 고르는 방식의 변동일 수 있음. 시드가 없는 모델이라 변동 범위를 재지 못함
- NAB 최적 임계값이 standard와 reward_low_FP_rate에서 0.92 이상으로 높게 잡힘. 0.5 고정 임계의 점수는 -118.1과 -111.7로 크게 깎임. 점수 0.5 이상인 레코드가 1.5퍼센트나 되는데 대부분 윈도우 밖이라는 뜻
- seasonal과 달리 Toto는 오탐 알림이 적음(0.5 기준 NAB 전체 4m 17건, 22m 5건). 이 모델의 약점은 오탐이 아니라 미탐

## 한계와 확인하지 못한 것

- 설정은 한 가지만 봄: 컨텍스트 512, 점수 상수 1.0, 1스텝 예측, 영샷. 컨텍스트 길이, 점수 상수, 예측 길이(다단계 예측의 누적 오차 사용 등)로 결과가 얼마나 달라지는지 측정하지 않음. NAB 점수는 임계값을 코퍼스에서 고르므로 점수 상수에는 둔감하지만 컨텍스트 길이에는 그렇지 않음
- 2.0은 미세조정을 지원하지 않아 도메인 적응을 해보지 못함
- NAB의 임계값은 평가 데이터로 맞춘 값이라 낙관적. 그런데도 낮음
- rrcf 비교값은 시드 0 하나. 3개 시드 평균은 20.4(범위 19.7에서 21.7)
- 장애 주입 평가는 이벤트 20개, 신호 4개의 작은 표본이고 5초 간격 실험실 데이터. 압축한 하루는 Toto가 보는 입력과 무관하지만 실제 1분 간격 운영 데이터와는 다름
- 장애 주입 데이터의 fixed, seasonal, rcf 수치는 이 문서 스크립트로 다시 계산한 값. 장애 주입 실험 쪽 최종 보고서와 대조하지 않음
- 운영 측정은 ARM64 CPU 한 종류, 시계열 500개, 합성 입력. x86, 더 큰 규모, 컨텍스트 512 외 값은 측정하지 않음
- 배치 경로와 스트리밍 경로가 같은 결과인지는 단위 시험(허용오차 구간 폭의 0.1퍼센트)으로 확인했고 NAB 전체에서 두 경로를 비교하지는 않음
- `toto` extra의 설치 크기와 시간은 재지 않음(다운로드는 네트워크가 느려 일부가 캐시에 있었음). 기본 설치 가벼움은 유지(extra가 없으면 torch를 불러오지 않음)
- PyPI `toto-2` 2.0.0이 GitHub 레포의 `toto2`와 같은 코드인지 대조하지 않음
- NAB 데이터 파일의 원 출처별 이용 조건은 2차 결과 문서와 같이 확인하지 못함
