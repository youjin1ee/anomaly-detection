# 3차 마일스톤 PoC: IBM Granite TSPulse

- 실행일: 2026-11-26
- 대상: `feat/m3-poc-tspulse` 브랜치(`feat/m2-integrate` f8e5898에서 분기), 모델 `ibm-granite/granite-timeseries-tspulse-r1` main 리비전(이상 탐지 권장 변형, allhead)
- 모델: Apache-2.0(코드와 가중치), 파라미터 약 1.08M, 파일 4.4MB. 코드는 `granite-tsfm` 0.3.12(`tsfm_public`), torch 2.11.0, transformers 5.24.1
- 실행 환경: ARM64 원격 장비, CPU 코어 3개로 제한, GPU 미사용, 다른 작업과 CPU를 나눠 써서 부하 평균이 9에서 26(코어 20개)이었음. 시간 수치는 참고용
- 방법 정의: `docs/evaluation.md`의 NAB 절과 같은 채점, 같은 파일별 파라미터 규칙(TSPulse는 파일별 파라미터 없음)
- 데이터: NAB 레포 커밋 `ea702d75cc2258d9d7dd35ca8e5e2539d71f3140`, 58개 시계열, 윈도우 116개. 장애 주입 데이터는 1차 실행분(run1)
- 모델 가중치와 데이터는 저장소에 없음

## 요약

- NAB standard 22.7점(최적 임계값 하나, 시드 없음, 결정적). 같은 조건 rrcf는 시드 0에서 21.7, 3시드 평균 20.4. 계절성 기준선은 0점
  - 공개 점수표 기준 AWS RCF 51.7, Numenta HTM 70.5(범위 윗값)보다 많이 낮고 Etsy Skyline 35.7보다 낮음. Bayesian Changepoint 17.7보다는 높음
  - 임계값 0.5 고정이면 standard가 -19.6. 최적 임계값이 0.9995로 포화 구간에 있고 0.5 이상 레코드가 전체의 0.93퍼센트(rrcf 0.26퍼센트)
- 헤드 중 pred(한 스텝 예측 오차)가 가장 좋았음: standard 26.7, reward_low_FN 39.1. time과 fft는 각각 16.7과 16.8. 세 헤드 최댓값 융합(기본값)은 22.7로 pred 단독보다 낮음
  - 헤드 선택은 라벨 검증셋이 있어야 가능해서 기본값은 융합으로 둠. 위 비교는 NAB 라벨을 보고 한 것이라 운영에서 같은 선택을 할 수 있다는 뜻이 아님
- 컨텍스트 512개와 정규화 이력 50개 때문에 첫 점수가 563번째 레코드에 나옴. 워밍업이 563보다 짧은 파일 15개에서는 점수 구간이 줄어듦. 나머지 43개 파일에서도 TSPulse 21.8, rrcf 21.4로 차이가 없어 워밍업이 짧다는 이유로 전체 순위가 바뀐 것은 아님
- CPU 3코어에서 시계열 1개 한 스텝 중앙값 48.9ms, 500개 한 스텝 4.0초(최대 4.5초), 모델 로드 4.9초, 최대 메모리 1.7GB. 1분 주기에 들어옴
- 장애 주입 데이터(run1, 이벤트 20개): 탐지 2개(recall 0.10), 오탐 2건. 같은 데이터에서 계절성 기준선은 13개(0.65), rcf는 3개(0.15). 합성 시나리오에서 TSPulse가 유리하다는 근거는 얻지 못함

## 어댑터 설계

모델 종류 `tspulse`(`models/tspulse.py`). 선택 의존성은 `pip install 'anomaly-detection[tspulse]'`

시계열마다 하는 일
- 최근 512개 값을 유지. 512개가 차기 전에는 값 없음을 반환
- 표준화: 윈도우 앞쪽 480개(뒤쪽 32개 제외)의 평균과 표준편차로 윈도우 전체를 표준화. 표준편차 하한은 평균 절댓값의 2퍼센트. 새 값이 척도를 키우지 않아 급변이 드러남. IBM 파이프라인은 시계열 전체를 한 번에 표준화하는데 스트림에서는 불가능해서 바꿈
- 추론: 한 번의 배치 순전파로 처리
  - 마스크 없는 윈도우 1개: 다음 값 예측(pred 헤드)
  - 최근 32개 값의 패치 4개를 하나씩 가린 윈도우 4개: 시간 영역 복원(time 헤드)과 주파수 가지 복원(fft 헤드)
- 헤드 오차: time과 fft는 최근 32개 값의 제곱 오차 평균(IBM 기본값 32). pred는 직전 스텝에서 낸 예측과 새 값의 제곱 오차
- score 0~1 매핑: 헤드 오차를 그 헤드 자신의 이력(최대 2000개)의 99분위수로 나누고 로지스틱으로 눌러 0~1로 만듦. 비율 2.0에서 0.5. rcf 모델과 같은 매핑이고 이력은 새 오차를 넣기 전 값. 이력이 50개 쌓이면 점수를 냄
- 헤드 융합: 세 헤드 점수의 최댓값. 모델 카드가 라벨 없는 경우 보고한 헤드 앙상블(최댓값 융합)을 따름. 라벨로 헤드를 고르는 triangulation은 운영에서 못 씀
- expected: pred 헤드의 한 스텝 예측(역표준화). 직전 윈도우로 만든 값이라 현재 값을 보지 않음
- lower, upper: expected 위아래로 `band_k`(기본 4.0) x 최근 512개 표준화 잔차의 로버스트 표준편차(MAD x 1.4826). TSPulse는 점수만 출력하므로 직접 만든 밴드. 근거는 잔차 분포가 밴드 폭을 정한다는 것뿐이고 포함 비율 같은 보정 측정은 하지 않음
- 첫 점수 시점: 512 + 1(첫 예측과 비교할 값) + 50(이력) = 563번째 샘플

구현 중 확인한 것
- 모델을 기본 설정으로 불러오면 호출마다 무작위 패치를 가려서 같은 입력의 결과가 달라짐. IBM 이상 탐지 예제처럼 `mask_type="user"`와 `num_input_channels=1`로 불러야 결정적이고 우리가 지정한 패치만 가려짐. 단위 시험이 같은 입력의 결과 일치와 배치 크기 무관을 확인
- 모델 카드의 1,536에서 2,048 포인트 요구는 IBM 오프라인 파이프라인에서 점수를 시계열 전체에 걸쳐 최소 최대 정규화하는 데서 나옴. 스트림은 그 정규화가 없어 512개 윈도우가 하드 최소고 나머지는 정규화 이력. IBM 파이프라인은 비인과적으로 윈도우 점수를 끝 32개의 중앙에 붙이는데(16포인트 앞당김) 스트림은 현재 시점에 붙여서 그만큼 늦음
- IBM 파이프라인의 `least_significant_scale`과 `least_significant_score` 보정은 쓰지 않음

경로
- 스트리밍: `update(timestamp, value)`
- 배치: `score_offline(values)`로 윈도우를 모아 배치 추론. 시계열 한 개의 평가용
- 시계열 여러 개: `update_many(models, values)`로 한 번의 순전파. 사이드카가 시계열 수백 개를 처리할 때 호출하는 용도
- 세 경로의 결과 일치는 실제 모델로 확인. 점수와 expected 차이 1e-3 이하를 단위 시험이 요구(`TSPULSE_MODEL_DIR`를 지정하면 실행)

## 운영 현실성 측정 (CPU만)

- 조건: 코어 3개 고정(`taskset`), torch 스레드 3, GPU 없음(`CUDA_VISIBLE_DEVICES` 빈 값), 주소 공간 상한 12GB. 측정 중 장비 부하 평균 약 9에서 10. 명령 `scripts/bench_tspulse.py --series 500 --threads 3`
- torch 2.11.0 CUDA 13 빌드를 CPU로 사용. 모델은 4.4MB지만 의존 패키지 설치 크기는 가상환경 4.8GB(CUDA 라이브러리 포함 휠). CPU 전용 torch 휠을 쓰면 줄어들 것으로 보이나 이번에 확인하지 않음

| 항목 | 값 |
|---|---|
| torch 임포트 | 1.6초 |
| 모델 로드 | 4.9초 |
| 로드 후 상주 메모리 | 737MB |
| 시계열 1개 한 스텝(워밍업 592스텝 뒤 200스텝) | 중앙값 48.9ms, p95 56.5ms, 최대 72.7ms |
| 시계열 500개 한 스텝(배치 한 번) | 중앙값 4.04초, 5회 4.01, 4.04, 3.92, 4.44, 4.52초 |
| 시계열 500개 처리 중 최대 메모리 | 1,698MB(시계열마다 윈도우와 이력 보관 포함) |

- 이전 예비 측정(부하 평균 26일 때)에서는 시계열 1개 중앙값 72.9ms, p95 322.7ms. 부하에 따라 꼬리가 크게 흔들림
- NAB 전체 실행: 코어 3개, 프로세스 3개(스레드 1개씩), 58개 파일 365,558 레코드를 2,982초에 처리. 레코드당 22.8ms(단일 프로세스, 배치 64)
- 판정: 1분 주기에 들어옴
  - 시계열 500개가 한 스텝 4.0초(주기의 7퍼센트), 코어 3개 기준. 시계열 수를 더 늘린 측정은 하지 않음
  - 시계열 1개씩 개별 호출하면 48.9ms로 500개가 24초. 배치 호출(`update_many`)이 6배 빠름
  - 사이드카가 지금 시계열마다 스레드를 두는 구조라 `update_many`로 묶는 변경이 필요. 이번 PoC는 파이프라인과 러너에 연결하지 않음
  - 비교: rrcf는 NAB에서 레코드당 14ms(단일 프로세스), seasonal은 0.083ms
- 모델 로드 4.9초와 패키지 임포트는 시작 시 한 번. 상주 메모리 737MB는 사이드카 한 개에 부담스러운 수준은 아니나 시계열 수에 비례하는 이력 메모리는 500개에서 측정한 값까지만 확인

## 장애 주입 데이터 평가

- 대상: 장애 주입 실험 1차 실행(run1)의 신호 4개(`signals.csv`), 라벨 20개 이벤트(`labels.json`). 완료 표시는 같은 폴더의 `report.md`(Completed events: 20). 2차 실행(run2-latency)은 수집 중이라 건너뜀. 폴더에 쓰지 않고 읽기만 함
- 방법: 장애 주입 실험 브랜치(커밋 e4d81f1)의 재생 모듈로 같은 라벨 대조, 같은 알림 규칙(0.5 이상 3개 연속), 간격 5초, 하루 1440초. 방향 보호(below, above)는 파이프라인과 같이 expected와 값의 차로 적용. 명령 `scripts/inject_tspulse_eval.py`(주입 브랜치의 `lab` 패키지 필요)
- 워밍업 4일(1152샘플)이라 TSPulse의 첫 점수(563번째)는 평가 시작 전에 이미 나옴. 윈도우 512개는 약 43분, 실험의 하루(1440초)보다 짧은 구간이라 일 주기를 보지 못함

- 이 데이터에서 주입이 신호를 움직인 정도가 작은 시나리오가 있음(주입 실험의 효과 크기 표에서 latency_rise 비율 중앙값 1.23). 놓친 이벤트 중 신호가 실제로 움직이지 않은 것이 몇 개인지는 가르지 않음
- 이벤트 20개, 시나리오당 5개라 recall 차이를 일반화하지 않음

## 한계와 확인하지 못한 것

- 성능 수치는 NAB와 주입 데이터 1회 실행뿐이고 TSPulse 논문의 TSB-AD 수치(융합 VUS-PR 0.44)와 직접 비교하지 않음. 시드 분산이 없는 결정적 모델이라 반복 측정이 아님
- NAB 점수의 임계값은 평가 데이터로 맞춘 값. TSPulse는 최적 임계값이 0.9995로 포화 구간이라 운영 임계값을 어떻게 잡을지는 열린 문제
- score 0~1 매핑(이력 99분위수 대비 비율 2.0에서 0.5)과 융합 방식은 NAB 점수를 보기 전에 정했고 이후 바꾸지 않음. 다른 매핑이나 `aggregation_length`(IBM 예제는 64)를 바꿔 보는 실험은 하지 않음
- 밴드(lower, upper)의 포함 비율은 측정하지 않음. 재생 평가는 점수만 사용
- 헤드별 점수는 같은 실행에서 얻은 것이고 헤드 선택(triangulation)은 라벨이 있어야 함. pred 단독이 융합보다 높게 나온 것은 NAB와 이 어댑터의 정규화에서 본 결과이며 다른 데이터에서 같다고 말할 수 없음
- IBM 파이프라인(오프라인, 전체 시계열 표준화, 최소 최대 정규화, 점수를 중앙에 정렬)과 이 어댑터의 결과가 같지 않음. IBM 방식 그대로의 NAB 점수는 측정하지 않음
- 가상환경이 CUDA 포함 휠 기준(4.8GB). CPU 전용 휠에서의 크기와 속도는 확인하지 않음
- 사이드카 러너와 `update_many`의 연결, 시계열 수천 개 규모의 선형성, 장기 실행 중 메모리는 확인하지 않음
- 2차 주입 실행(run2-latency)은 수집 중이라 평가하지 않음
- 2차 마일스톤 rrcf와 계절성 기준선 점수는 다시 돌리지 않고 기록된 시드 0 점수를 썼음. 같은 코드라는 점은 브랜치 분기점으로만 확인함
