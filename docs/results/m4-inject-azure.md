## 트레이스 축소와 압축

### 도착률 축소

- 원 트레이스 code는 7일에 16803695건(평균 약 28건/초). 한 대 용량에 맞춰 요청을 같은 확률로 솎아냄(유지 확률 0.00303, 50883건 유지)
- 솎아낸 요청은 도착 시각, 입력 길이, 출력 길이를 그대로 유지. 일 주기, 주말 저하, 입력과 출력 길이의 결합 분포가 원본 모양
- 랩 평균 도착률 2.02건/초(7일 평균), 월에서 목 평균 2.61건/초
- 근거는 용량 확인(`examples/inject-azure/calibrate.sh`). 월요일 17시에서 21시(UTC) 피크 구간을 10분 재생

| 평균 도착률 설정 | 완료 요청/초 | 첫 토큰까지 평균(초) | 대기 요청 중앙값, 90분위, 최대 | 실행 중 요청 중앙값, 최대 | 토큰 간 지연 평균(ms) |
|---|---|---|---|---|---|
| 2 | 5.39 | 0.22 | 0, 0, 0 | 5, 15 | 61 |
| 4 | 10.68 | 2.73 | 8.5, 95, 119 | 29.5, 32 | 138 |

- 설정 4는 동시 시퀀스 상한 32에 붙어 대기열이 쌓임(포화). 설정 2는 대기 0, KV 캐시 사용률 최대 9%
- 설정 2의 피크 처리량 5.4건/초는 포화 시 처리량 10.7건/초의 약 절반. 처리량 하락 주입이 대기열 포화와 섞이지 않도록 2로 결정
- 설정 6도 시도했으나 포화가 이미 확인되어 끝내지 않고 중단

### 길이 상한

- 엔진의 KV 캐시가 12288토큰이라 원본 입력(중앙값 1934, 평균 2508, 최대 7743토큰)을 그대로 보낼 수 없음
- 입력 길이에 0.2를 곱하고(중앙값 387, 평균 502, 99분위 1537) 상한 1700. 상한에 걸린 요청 0건
- 출력 길이는 상한 256(원본 99분위 271). 상한에 걸린 요청 1.1%. 평균 19.6토큰(원본 22.8), 중앙값 8로 같음
- 입력만 배율로 줄여 분포 모양은 유지했지만 입력 절대 길이는 원본의 0.2배. 프리필 부담이 실제보다 가벼움

### 시간 압축과 왜곡

- 압축 비율 24배(1일 3600초). 7일 7시간 안에 끝내고 모델이 합성 랩보다 긴 일 주기를 2회 이상 보게 하려는 선택
- 합성 랩은 1일 24분(60배)이었음. 이번 압축이 더 약해 1분 `rate()` 창이 하루에서 차지하는 비중이 작음(1.7%, 지난 랩은 4.2%)
- 지연 계열 지표(토큰 간 지연 등)는 실시간 값이라 압축되지 않음. 트레이스 시간 1분에 해당하는 랩 시간은 2.5초지만 요청 처리 시간은 그대로
- 솎아내기로 원본의 순간 폭주(초 단위)가 없어지고 도착이 포아송에 가까워짐
- 알림 규칙 3샘플(15초)은 트레이스 시간 6분에 해당. 이벤트 지속 125초에서 238초는 트레이스 시간 50분에서 95분
- 오탐 비율은 두 방식으로 표기. 압축일 기준은 랩 3600초당 건수이고, 압축이 충실하다면 실제 1일당 건수와 같다고 볼 수 있음. 랩 24시간 기준은 랩 86400초당 건수로 압축일 기준의 24배
- 지연은 랩 초(실제 경과)와 트레이스 분(랩 초에 24를 곱해 60으로 나눈 값) 둘 다 표기
- 주 단위 주기는 모델이 다루지 않음. 워밍업 3일에 주말 이틀이 들어 있음

## 주입과 신호 효과

- 시나리오는 요청량 급락, 출력 길이 급감, 처리량 하락. 지연 증가는 이번에 뺌(지난 랩에서 어느 모델도 못 잡았고 클라이언트 읽기 지연의 시뮬레이션이었으며 엔진 쪽 지연을 root 없이 만들 방법을 찾지 못함)
- 요청량 급락: 도착률 0.03배. 출력 길이 급감: 출력 토큰 상한 1에서 3. 처리량 하락: 같은 GPU의 경쟁 행렬곱 프로세스

  - 보정 조건: 입력 0.15배, 입력 상한 1500, 출력 상한 512(상한에 걸린 요청 3.3%), 수요일 12시에서 16시(UTC) 피크 10분 재생
  - 평균 도착률 1: 완료 1.42건/초, 첫 토큰까지 평균 0.12초, 요청 평균 3.87초, 토큰 간 지연 41ms, 실행 중 요청 중앙값 5와 최대 9, 대기 0, 오류 0
