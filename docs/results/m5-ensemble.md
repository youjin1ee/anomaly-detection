## 요약

- 데이터마다 단일 모델 최고가 다름. 같은 평가 구간 기준 F1 최고 단일 모델은 NAB awsrcf-nab, SMD subpca, PSM subpca(AI 단계)와 awsrcf(사람 단계), Azure 장애 주입 fixed
- 모델마다 시계열별 보정 구간(워밍업 뒤 3일)의 점수 분포로 점수를 -log10 꼬리 확률(놀람 값)로 바꿔 한 척도에 맞춘 뒤 조합. 두 단계 임계는 같은 조합 점수에서 예산 1건/일과 0.1건/일로 뽑음
- 추천 구성: awsrcf-nab, subpca, fixed의 평균(`mean3+rules`)에 규칙 층(방향 제한, 최소 밴드, 희소 제외, 0 하락 전용)을 결합. 선정 기준은 라벨 있는 4개 데이터의 두 단계 F1 평균이 가장 높은 구성(AI 단계 0.473, 사람 단계 0.470). 같은 기준에서 단일 모델 최고는 AI 단계 0.406(awsrcf, SMD 제외 평균)과 0.388(subpca), 사람 단계 0.348(awsrcf-nab)
- 운영 규칙(0.5 이상 3연속) 단일 모델 최고 F1은 raw:awsrcf 0.411이지만 오탐이 단위일당 4.44건. 추천 구성의 AI 단계는 F1 0.473에 오탐 0.98건
- 데이터별로 보면 추천 구성이 단일 최고보다 높은 경우가 8칸 중 5칸(NAB 두 단계, SMD 사람, PSM 사람, Azure AI). 낮은 경우는 SMD AI -0.012, PSM AI -0.058. 한 칸은 같음(Azure 사람)
- 개선 폭은 데이터마다 고르지 않음. 앙상블의 이점은 평균 F1 상승 약 0.06에서 0.12와 데이터별로 모델을 고를 필요가 없다는 점. 데이터별 최고 모델을 미리 알고 고른 경우와 비교하면 가장 크게 진 칸이 PSM AI(-0.058)
- 라벨 없는 데이터에서 추천 구성의 사람 단계 알림은 BOOM 0.080건/일(예산 충족 77%), 사내 재생 0.026건/일(94%). 목표 0.1건/일 안. AI 단계는 BOOM 0.485건/일, 사내 재생 0.169건/일로 목표 1건/일 안
- 목표 예산은 라벨 있는 데이터에서 지켜지지 않음. 사람 단계 오탐이 NAB 0.029, PSM 0.190, SMD 0.988건/단위일로 목표 0.1을 PSM과 SMD에서 넘음. 보정 구간에 이상이 섞여 있고 평가 구간에서 분포가 달라지기 때문으로 보이나 원인을 분리해 확인하지는 않음
- 꼬리 외삽을 끄면(`@max`) 라벨 있는 데이터에서 탐지율이 오르고(사람 단계 0.459에서 0.690, or3+rules 기준) 라벨 없는 데이터에서 알림이 늘어남(BOOM 사람 단계 0.194에서 0.310건/일, 사내 재생 0.060에서 0.152건/일). 외삽은 미탐을 늘리는 대신 오탐을 줄임
- 이 평가는 모델 점수를 새로 만들지 않고 캐시를 읽음. 보정 구간, 평가 구간 분리와 구성 고정을 지켰으나 구성 후보는 첫 실행 결과를 본 뒤 `mean3+rules`와 운영 규칙 기준선(`raw:`)을 추가함

- 보정 구간과 평가 구간은 겹치지 않음. 알림은 평가 구간에서만 셈. 보정 구간에 끝나는 이벤트는 제외, 걸친 이벤트는 평가 시작부터로 자름
- 보정은 점수만 보고 라벨은 보지 않음. 보정 구간의 이상은 정상으로 취급되어 임계를 올림
- 보정 구간 길이는 설정(`cal_days`, 기본 3일). 하루 샘플이 적은 시계열은 최소 300샘플로 늘림
- 알림 규칙은 `docs/evaluation.md`와 같음(3연속, 간격 10 이하 병합, 이벤트 끝 5샘플 뒤까지 인정)
- 예산은 단위당 하루 알림 수. AI 분석 단계 1건, 사람 단계 0.1건(설정값)
- 구성은 전 데이터 공통으로 고정. 데이터별 튜닝 없음
- 구성 이름: `fixed`, `seasonal`, `subpca`, `awsrcf-nab`, `awsrcf`는 단일 모델을 같은 보정과 두 단계 임계로 낸 것. `or2`는 awsrcf-nab와 subpca의 최댓값. `or3`, `mean3`, `vote2of3`는 awsrcf-nab, subpca, fixed의 최댓값, 평균, 3개 중 2개 동의. `route`는 지표 종류별 라우팅. `+rules`는 규칙 층 결합. `or3+seasonal`은 비교용. `raw:`는 보정 없이 원점수 0.5 이상 3연속인 운영 규칙(두 단계 같은 값). `@max`는 꼬리 외삽 없이 보정 구간 최댓값으로 임계를 잡은 것
- 지표 정의: `docs/evaluation.md`. 침묵은 보정 구간에 점수가 없거나 임계가 상한을 넘어 그 단계가 절대 울릴 수 없는 단위의 비율

보정 방식과 근거(요약, 자세한 내용은 `docs/design.md`)

- 모델과 시계열마다 보정 구간 점수에서 놀람 값 `x = -log10 p`를 만듦. 90분위까지는 경험 분포, 그 위는 일반화 파레토 꼬리(확률가중적률 추정)로 외삽
- 짧은 보정 구간의 최댓값이 이후 꼬리를 대표하지 못하는 문제(BOOM 보정 사전 실험에서 하한 없이 예산의 2.5배에서 5배 초과, 하한 0.5에서는 일부 시계열이 침묵)를 피하려고 꼬리 모델을 씀
- 두 단계 임계는 조합 점수의 알림 군집 정점에 지수 꼬리를 맞춰 예산에 해당하는 수준을 읽음
- `@max` 행과 비교해 이 외삽의 효과를 확인

### 조합 방식 비교에서 읽은 점

- 평균과 투표는 단독 모델의 우연한 고점을 눌러 오탐을 줄임. 최댓값(or)은 탐지율이 가장 높지만 오탐도 가장 많음
- 투표(vote2of3)는 AI 단계 F1이 높으나(0.484) 사람 단계에서 임계가 너무 높아져 탐지율 0.213으로 떨어짐. 사람 단계 F1 0.274

## 알려진 한계

- 라벨 있는 데이터의 예산 초과: 보정 구간(3일)에 이상이 섞이면 임계가 올라가고, 평가 구간에서 분포가 달라지면 오탐이 예산을 넘음. SMD는 보정 구간(시험 구간 앞 3일)에 이상이 많음
- 서버 단위(SMD, PSM)는 차원별로 보정한 뒤 최댓값을 취하고 서버에 예산을 적용. 차원 수가 많으면 최댓값이 오탐을 키움
- Azure 장애 주입의 보정 구간 2일에는 트레이스의 주말 저하가 들어 있음. 이벤트 24건이라 구간이 넓음
- 사내 재생과 BOOM은 라벨이 없어서 탐지율을 모름. 알림이 적다고 좋은 구성이라고 할 수 없음
- 추천 구성 선정에 쓴 데이터와 평가 데이터가 같음. 교차 검증을 하지 않음. 구성 후보는 첫 실행 결과를 본 뒤 `mean3+rules`와 `raw:`를 추가함
- 모델 점수는 시드 0 하나. awsrcf는 SMD 8대만 있어 SMD에서 평가하지 않음
- toto와 tspulse는 전 데이터에 캐시가 없어 앙상블 구성에 넣지 않음
- 스트리밍 사이드카 모델은 배열 경로와 같은 점수를 내는 것을 합성 시계열 시험으로만 확인. 실제 장비에서 사이드카 실행은 하지 않음

## 미묘한 장애 데이터

- 별도 에이전트가 미묘한 장애 주입을 반복 실행하며 덤프, 라벨, 점수 캐시를 모으는 중이라 이 문서의 평가에 포함하지 못함(작성 시점에 완성된 실행 없음)
- 완성된 실행 폴더(`signals.csv`, `labels.json`, `scores/` 포함)가 생기면 다음 명령 하나로 평가. 점수 캐시에 fixed, seasonal, subpca, awsrcf-nab, awsrcf가 모두 있어야 하며 없으면 `anomaly_detection.lab.azure_report`를 `--cache-dir RUN/scores`로 먼저 돌림

```sh
anomaly-detection-ensemble run --out out/subtle.json --lab-dir subtle=RUN_DIR && anomaly-detection-ensemble report out/subtle.json
```

- 일괄 스크립트로 전체를 다시 낼 때는 `LAB=subtle=RUN_DIR scripts/ensemble_eval.sh OUT_DIR`
